# bmug2 GUI ↔ CLI compatibility

bmug2 ships two halves that must be kept in lock-step:

- **shell CLI** — `bin/backmeup.*.sh` scripts installed under `${BMU_INSTDIR}/bin/` (typically `~/usr/bmu/bin/`). Version lives in `BMU_VERSION` inside the installed `backmeup.setup.sh`.
- **desktop GUI** — Tauri app bundle (`/Applications/bmug2.app` on macOS, `.deb`/`.AppImage`/`.rpm` on Linux). Version lives in the bundle's `Info.plist` / its compiled `env!("CARGO_PKG_VERSION")`.

Each release of bmug2 bumps both halves together via the 6-file version bump recipe (see `CLAUDE.md`). As long as users upgrade both halves together, the halves match exactly and no compatibility concern arises.

**This document covers what happens when they drift.**

## Policy: asymmetric

The two drift directions are not equivalent.

| Direction | What happens | Policy | Mechanism |
|---|---|---|---|
| **GUI > CLI** | GUI may call flags / parse JSON fields the CLI doesn't understand yet | **Allowed, per-feature gated** | `MIN_VERSION_FOR_*` constants in `gui/src-tauri/src/replication.rs` + `MIN_COMPATIBLE_VERSION` baseline in `version.rs`. Each gate surfaces a clear "upgrade CLI to vX.Y.Z" error when hit. |
| **GUI == CLI** | lock-step, ideal | **Silent** | n/a |
| **GUI < CLI** | GUI's own write paths (schedule install, replication config, source ignores, launchd plists) are the STALE code against a current CLI. GUI writes outdated artifacts that silently undo fixes landed in the CLI side. | **Hard-gate** on release builds | `version::check_cli_not_newer()` refuses to set up an install when installed CLI > GUI's own version. |

### Why the asymmetry

The GUI is both a viewer and an **author** of on-disk artifacts:

- **Wrapper scripts** — `~/Library/Application Support/.../schedules/*.sh` is generated by `schedule::install()`'s Rust code.
- **Replication config** — written via the GUI invoking `backmeup.configure.sh --replicate-* flags`.
- **Source ignore settings** — `.bmuconfig` + `.bmuignore` written by `ignore::save()`.
- **launchd `.plist` / systemd `.service` units** — written by `schedule::install()`.

A **stale GUI** against a **current CLI** writes stale output. The CLI's own shell paths behave correctly on its own data, but the GUI's write paths skip new fixes because the write code hasn't been updated yet.

Confirmed in the wild (Nov 2026): a user on GUI 2.18.17 + CLI 2.18.22, re-saving a HouseKeeping schedule, would get the pre-#186 wrapper (missing the local-backend `replicate.sh` call) written back to disk — undoing what the #197 reconcile would have fixed had the GUI been current.

## Per-feature gates currently in effect

As of v2.18.22, the GUI enforces these minimums on the installed CLI:

| Feature | Min CLI | Rationale |
|---|---|---|
| `MIN_COMPATIBLE_VERSION` | **v2.11.0** | GUI's ignore-settings editor (`.bmuconfig` / `.bmuignore`) is silently ignored by older CLIs that don't read those files. |
| `MIN_VERSION_FOR_FLAGS` | **v2.14.0** | `--replicate-backend=/--replicate-remote-sync=/--replicate-remote-backups=/--replicate-proton-remote=` flags on `backmeup.configure.sh`. |
| `MIN_VERSION_FOR_LOCAL` | **v2.18.7** | `local` as a valid `--replicate-backend` value. |

Any PR that adds a GUI feature depending on a CLI change bumps the matching gate — see those constants' own doc comments for the pattern.

## Developer workflow

Debug builds **skip** the GUI-not-newer-than-CLI hard-gate (`cfg!(debug_assertions)` short-circuit), so a dev running the GUI from source against a locally-installed older CLI isn't blocked. Release builds enforce strictly.

Testing the hard-gate's inner logic regardless of build mode: call `version::check_cli_not_newer_inner(bin_dir, gui_version)` directly — same function the public wrapper uses, minus the debug-mode escape.

## What the user sees

### GUI < CLI (hard-gate fires)

```
bmug2 CLI at /Users/you/usr/bmu/bin is v2.18.24 - newer than this
GUI (v2.18.22). The GUI writes config, schedule wrappers, and
replication settings that must be generated by a GUI at least as
new as the CLI; running a stale GUI against a newer CLI silently
undoes fixes landed in between. Update the GUI from
https://github.com/mariotti/bmug2/releases.
```

The GUI falls back to the setup screen rather than opening the dashboard.

### GUI > CLI (feature gate fires, if the user hits an affected feature)

Error surfaces per-feature in context, e.g. when saving replication settings:

```
This GUI needs bmug2 v2.14.0+ to configure replication, but the
installed CLI is v2.13.0. Upgrade the CLI there and re-run
backmeup.configure.sh.
```

Other features of the GUI keep working.

## Release-cycle contract

Every tagged release lock-steps GUI and CLI via the 6-file version bump:

- `bin/backmeup.configure.sh`  →  `BMU_VERSION`
- `gui/package.json`  →  `version`
- `gui/package-lock.json`  →  `version` (×2)
- `gui/src-tauri/tauri.conf.json`  →  `version`
- `gui/src-tauri/Cargo.toml`  →  `version`
- `gui/src-tauri/Cargo.lock`  →  `version` (for the `gui` crate)

`tests/test_backmeup.sh::testGuiVersionStaysInSyncWithBmuVersion` is the CI-level regression guard that fails any PR where one of the five GUI files has drifted from `BMU_VERSION`.
